Jev Rover Autopilot

Five ways to let Jev drive the rover. Jev reads the rover's telemetry and orientation plus a text description of the camera view, picks the next move, and sends it back. Both AP control pages keep working the whole time, and a new Jev Auto mode sits next to Manual and Autonomy.

Background

What Jev is, in rover terms

Jev is a "System 1" decision model from Typesafe AI. A chat LLM writes text word by word. Jev works differently: you send it a state (plain text describing the situation) plus a few typed questions, and it answers all of them in one shot, each answer with a probability. For a rover, the useful question is "which of these allowed moves should I make next?"

70–500 msend-to-end per decision, according to published tests
3 question typesnoul yes/no · choice pick one · score low/med/high
Text onlyNo image input documented, so the camera view has to become text first
$0.042 / Minput tokens; output is free. One decision per second costs pennies a day

Good at

  • Fast, repeated choices from a fixed list of actions
  • Yes/no checks such as "is the path ahead blocked?"
  • Scoring risk (terrain roughness, tilt danger)
  • Several questions in one call at no extra latency

Weak at

  • Arithmetic and unit comparisons. Do those in code first, then pass the result as words ("obstacle 38 cm ahead, under the 40 cm limit")
  • Long or noisy state. Accuracy drops when the context is bloated
  • Writing reports or explanations. That's a job for an LLM such as Claude
  • Real hardware. Public demos so far are simulators and robot arms in MuJoCo

Jev is new, and most public details come from third-party write-ups (see sources at the end). Before building, check the exact request format for choice questions, the rate limits and the auth in Typesafe's own docs. The JSON on this page is illustrative.

Common to all five options

The parts that never change

Whichever architecture you pick, the rover firmware gets the same three additions. Only the transport between the boards and Jev differs between options.

1. A third drive mode

The rover's AP page gets a Jev Auto button next to Initiate Autonomy and Manual Propulsion. Any manual press on either AP page drops Jev Auto immediately, so a human can always take over.

stateDiagram-v2
  [*] --> MANUAL
  MANUAL --> AUTONOMY: Initiate Autonomy
  AUTONOMY --> MANUAL: Abort
  MANUAL --> JEV_AUTO: Jev Auto
  JEV_AUTO --> MANUAL: Abort or any manual press
  JEV_AUTO --> SAFE_STOP: no command for 1.5 s, tilt, obstacle under 20 cm
  SAFE_STOP --> JEV_AUTO: fresh command and path clear
  SAFE_STOP --> MANUAL: Abort

2. Reflexes on the rover always win

  • Obstacle veto: the ultrasonic sensor stops forward motion under 20 cm, whatever Jev says.
  • Tilt veto: pitch or roll over 35° stops the motors.
  • Watchdog: no fresh command for 1.5 s means stop. If the network drops, the rover halts instead of driving blind.
  • Short moves only: each command lasts at most 500 ms, then the rover waits for the next one.
  • Confidence gate: if Jev's top action is under 0.6 probability, the rover stops or falls back to the existing ultrasonic autonomy.

3. One command format

Whatever carries it (HTTP, a database row or MQTT), a command looks like this:

{
  "seq": 4182,
  "action": "turn_right",    // forward | turn_left | turn_right | reverse | stop
  "speed": 180,              // 0-255, clamped on the rover
  "duration_ms": 300,        // max 500
  "confidence": 0.87,
  "issued_at": 1759581234567
}

The rover rejects out-of-order seq numbers and commands older than 1 s.

Your teammate's contract: the camera description

Jev can't see images, so a vision model (Claude, Gemini or similar) turns each frame into a short description. Keep it structured and small, because long state makes Jev less accurate.

{
  "frame_id": "capture_83211_42.jpg",
  "captured_at": 1759581233900,
  "summary": "Chair leg about 50 cm ahead, slightly left. Open floor to the right.",
  "obstacle_ahead": true,
  "clear_side": "right",           // left | right | both | none
  "hazards": ["cable on floor"]
}

The camera uploads every 10 s today. For Jev Auto it needs a frame every 1–2 s.

The Jev call each cycle

Code turns the numbers into words before Jev sees them. Jev is weak at arithmetic, so "62 cm" becomes "clear, above the 40 cm limit".

POST  Typesafe Jev API   (illustrative)
{
  "state": "Mode: explore. Front distance: 62 cm (clear).
            Pitch 3 deg, roll -1 deg (level). Terrain: smooth.
            Last move: forward 300 ms.
            Camera 0.4 s ago: chair leg ~50 cm ahead slightly left;
            open floor to the right. Hazard: cable on floor.",
  "questions": {
    "next_action": { "type": "choice",
      "options": ["forward","turn_left","turn_right","reverse","stop"],
      "instructions": "Safest move that keeps exploring" },
    "path_blocked": { "type": "noul",
      "instructions": "Something blocks the path straight ahead" },
    "terrain_risk": { "type": "score",
      "levels": ["low","medium","high"] }
  }
}
→ next_action: turn_right 0.87 · path_blocked 0.81 · terrain_risk low
OPTION 01

On-board brain: the rover calls Jev itself

no extra machineAPI key on device~0.6–1.5 s / move

The ESP32 builds the state string from its own sensors, fetches the latest camera description from Supabase, calls Jev over HTTPS and runs the answer. Your teammate's vision step runs in the cloud and writes descriptions into camera_captures.

flowchart LR
  subgraph Rover["ESP32 rover"]
    S["Sensors: ultrasonic, MPU6050, BMP280, DHT11"] --> B["Build state text"]
    B --> J1["HTTPS call to Jev (core 0 task)"]
    J1 --> X["Execute move with reflex veto"]
    AP1["AP page: Manual / Autonomy / Jev Auto"] --> X
  end
  subgraph Cam["ESP32-CAM"]
    C["Capture every 1-2 s"] --> U["Upload JPEG"]
    AP2["AP live view"]
  end
  U --> ST[("Supabase Storage")]
  ST --> V["Vision model writes description (teammate)"]
  V --> DB[("camera_captures.description")]
  DB -->|"poll latest"| B
  J1 <--> JEV["Jev API"]

Pros

  • Fewest moving parts. Nothing else has to be running.
  • Fresh sensor data, because the rover reads it directly.
  • Works anywhere the rover has WiFi with internet.

Cons

  • The Jev API key lives in firmware, and anyone with the board can dump it. That's a bad fit for a public repo.
  • HTTPS calls block for hundreds of ms. The call must move to a FreeRTOS task on core 0, or the AP page freezes.
  • TLS uses a lot of the ESP32's RAM next to the web server.
  • Every prompt tweak means reflashing the rover.

OPTION 02

Supabase cloud brain: Edge Functions decide

keys stay server-sidefull decision log~1–2 s / moveinternet required

You already use Supabase, so let it host the brain. Both boards keep writing to tables. A database webhook triggers a describe function when a new image arrives and a decide function when new telemetry arrives. decide calls Jev and writes a row to a new rover_commands table. The rover picks commands up over Supabase Realtime (a websocket) or by polling every 500 ms.

flowchart LR
  R["ESP32 rover"] -->|"telemetry every 0.5-1 s"| T[("sensor_readings")]
  C["ESP32-CAM"] -->|"JPEG every 1-2 s"| ST[("Storage: rover_images")]
  ST -->|"insert webhook"| FD["Edge Function: describe (teammate)"]
  FD -->|"vision model"| CC[("camera_captures.description")]
  T -->|"insert webhook"| FJ["Edge Function: decide"]
  CC --> FJ
  FJ <--> JEV["Jev API"]
  FJ --> CMD[("rover_commands")]
  CMD -->|"Realtime or poll"| R
  AP1["Rover AP page"] -.-> R
  AP2["Cam AP page"] -.-> C

Pros

  • The Jev and vision keys live in Supabase secrets, never on a board.
  • No extra hardware or laptop needs to stay on.
  • Every state, decision and image is stored, so you can replay a run and see why the rover turned.
  • Clean split: your teammate owns describe, you own decide.

Cons

  • Each decision makes several network hops, so the rover reacts slowly.
  • No internet means no Jev Auto. The rover falls back to its reflexes.
  • Many writes per second can hit free-tier limits.
  • Edge Function cold starts add delay after idle periods.

OPTION 03

Ground station: a laptop or Raspberry Pi runs the loop

fastest to build and tweakkeys on laptop~0.3–0.8 s / movelaptop must stay on

A small Python service ("Earth Station") runs on a laptop or Pi on the same WiFi as both boards. It reads the rover's existing /sensors/data endpoint several times a second, grabs frames from the camera's existing /capture endpoint, has them described, asks Jev, and sends the move to a new /jev/cmd endpoint on the rover. It can still log everything to Supabase.

flowchart LR
  subgraph LAN["Same WiFi router"]
    R["ESP32 rover: /sensors/data, /jev/cmd"]
    C["ESP32-CAM: /capture"]
    subgraph GS["Earth Station (Python)"]
      P1["Poll telemetry 5 Hz"] --> SB["State builder"]
      P2["Grab frame 1 Hz"] --> VD["Describe frame (teammate module)"]
      VD --> SB
      SB --> JC["Jev client"]
      JC --> SF["Safety gate + rate limit"]
    end
  end
  R --> P1
  C --> P2
  JC <--> JEV["Jev API"]
  VD <--> VLM["Vision model API"]
  SF -->|"POST /jev/cmd + token"| R
  GS -.->|"log runs"| DB[("Supabase")]
  PH1["Phone on rover AP"] -.-> R
  PH2["Phone on cam AP"] -.-> C

Pros

  • Prompt and logic changes take seconds. Restart a Python script; no reflashing.
  • Fresh local data with no cloud round trip, so it's the lowest latency here.
  • Reuses the endpoints both boards already have. The rover only needs /jev/cmd and the Jev Auto mode.
  • Keys stay on one machine you control.
  • Your teammate can build the describe module as a plain Python function and test it on saved images.

Cons

  • A laptop or Pi has to be running and nearby.
  • Both boards must join the same router. Today the rover uses one network and the camera another.
  • /jev/cmd needs a token, or anyone on that WiFi could drive the rover.

OPTION 04

MQTT event bus: every part talks through topics

push, not pollingparts fully decoupled~0.3–1 s / movenew infrastructure

An MQTT broker (Mosquitto on a Pi, or a free hosted broker such as HiveMQ Cloud) carries every message. The rover publishes telemetry and subscribes to commands. The camera publishes frames, or frame URLs. A vision worker and a Jev agent each subscribe to what they need and publish their results. Every part can run anywhere and be restarted on its own.

flowchart LR
  R["ESP32 rover"] -->|"rover/telemetry 5 Hz"| BR(("MQTT broker"))
  C["ESP32-CAM"] -->|"cam/frame_url 1 Hz"| BR
  BR -->|"cam/frame_url"| VW["Vision worker (teammate)"]
  VW -->|"cam/description"| BR
  BR -->|"telemetry + description"| JA["Jev agent"]
  JA <--> JEV["Jev API"]
  JA -->|"rover/cmd"| BR
  BR -->|"rover/cmd"| R
  R -->|"rover/status: mode, ack"| BR
  BR -.->|"optional"| LOG["Logger to Supabase"]
  AP1["Rover AP page"] -.-> R
  AP2["Cam AP page"] -.-> C

Pros

  • Messages arrive as they happen, with no polling delay.
  • Each of you owns your own topics and can test against recorded messages.
  • Easy to add later: a live dashboard, a second rover, a data logger.
  • Works across networks when the broker is hosted.

Cons

  • One more system to learn and run: the broker, topic design and QoS settings.
  • MQTT over TLS on the ESP32 needs certificates set up.
  • The Jev agent and vision worker still need a host (laptop, Pi or cloud VM).

OPTION 05

Layered autonomy: reflexes, Jev and an LLM planner

smartest behaviouruses each model for its strengthmost complextwo AI vendors

This works the way real rovers do: three layers running at three speeds. The ESP32 handles reflexes many times a second. Jev chooses each move several times a second. A slower LLM such as Claude looks at the bigger picture every 10–20 s. It sets a goal ("explore the open area on the right, avoid the chair") that goes into Jev's state, and it writes the mission report the old n8n workflow used to produce. This layer sits on top of the transport from option 3 or 4.

flowchart TB
  subgraph T2["Tier 2: planner, every 10-20 s"]
    LLM["LLM (Claude): read descriptions + telemetry history"] --> G["Current goal + mission report"]
  end
  subgraph T1["Tier 1: Jev policy, every ~300 ms"]
    ST["State: goal + telemetry + latest description"] --> JEV["Jev: choice of next move"]
  end
  subgraph T0["Tier 0: ESP32 reflexes, every loop"]
    RF["Obstacle veto, tilt veto, watchdog, manual override"] --> M["Motors"]
  end
  CAM["ESP32-CAM frames"] --> VD["Vision description (teammate)"]
  VD --> ST
  VD --> LLM
  TEL["Rover telemetry"] --> ST
  TEL --> LLM
  G --> ST
  JEV -->|"command"| RF
  AP["Both AP pages"] -.-> RF

Pros

  • Jev does the fast, narrow choices it's built for, and the LLM does the reasoning and writing.
  • The rover follows a goal instead of wandering, and the decisions are explainable.
  • Brings mission reports back without n8n.
  • The reflex tier keeps the hardware safe if either model misbehaves.

Cons

  • The most code and the most things to debug.
  • Two AI APIs to pay for and keep keys for.
  • Only worth it once a simpler loop already drives reliably.

Recommendation

Start with the ground station (3), grow into layered autonomy (5)

Option 3 gets Jev driving with the least new code. It reuses endpoints both boards already have, keeps every key off the hardware and the public repo, and lets you tune the Jev prompt in seconds while you learn how it behaves. Design the command format and topics so the loop can later move to MQTT (4) without changing the rover's logic. Then add the planner tier (5) once Jev drives reliably. Skip option 1 for this project: a key in public firmware is a leak waiting to happen.
